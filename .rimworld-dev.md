# Realistic Bases development settings

Shared workflows are vendored at `.shared/rimworld-dev-skills` and discovered
through `.agents/skills` and `.claude/skills`. Read `.rimworld-dev.json` for this
checkout's project, tests, shipped DLLs, reset save, and baseline active-mod order.
The shared snapshot works after an ordinary clone without a sibling skills repo.
Update it from a clean checkout with:

```sh
sh .shared/rimworld-dev-skills/scripts/update-subtree.sh
```

The default source is the published `RimWorld-mods-patches/rimworld-dev-skills`
repository's `main` branch. Optional source/ref arguments override it.

## Consumer-specific assertions

- Framework/reference pin: net472 / RimWorld 1.6.4871; check the project before changing it.
- Full planner/garrison and layout suites are configured. For focused layout tests,
  append `-- --only P4D` (or another matching name); the full suite takes minutes.
- Only `RealisticBases.dll` belongs in `1.6/Assemblies/`.
- The existing immutable reset point is `RealisticBases-P0-Disposable.rws` under
  `.runtime/rimworld-dev-profile/Saves`. Preserve it. If absent in a fresh clone,
  create a disposable developer colony explicitly; do not import normal saves.
- Require the configured five-mod baseline in the profile and loaded-mod log.
  Optional HugsLib/Geological Landforms/Map Preview tests restore it afterwards.
  Use lowercase package IDs in hand-edited optional-mod entries: vanilla's active
  mod hash lookup lowercases queries, while a mixed-case XML entry can load the
  mod yet make `ModsConfig.IsActive` falsely report it inactive.
- Confirm `GAME_LOADED` plus the native autoload/profile log evidence at startup.
- For procedural generation, use exact action `Generate playable flat P4 settlement`
  and fresh `event=PROCEDURAL_SPAWN_COMPLETE\b`, failing on
  `event=PROCEDURAL_(PLAN|SPAWN)_REJECT\b`. A successful API invocation or
  `DEBUG_SETTLEMENT_READY` alone is not acceptance.
- `Use high-industrial P4 stage once` is a synchronous setup action, not generation.
- `Use neolithic P4 stage once` explicitly tests primitive research/equipment
  legality. `Use tribal profile for next generation` changes the settlement
  profile, not its faction-derived tech stage; require the actual stage in the
  fresh procedural-plan event before counting primitive coverage.
- `Generate isolated hostile P0 settlement` can unload without a player pawn;
  `Generate playable hostile P0 settlement` moves one disposable colonist to keep
  it loaded for tick-based P2/P3 checks. These mutate only the development save.
- `Audit current P3 defensive encounter` must target the encounter map. Verify
  defender bounds/positions, player control, mortar ammunition/barrels, power,
  controller transitions, and save/reload restoration against logs and actual
  pawns, not screenshots alone. Recheck map and pause state after arrival/reload.
- For a fresh one-to-three-mortar P4E magazine case, `Start P4E mortar magazine loading
  probe` requires untouched twelve-HE magazine stocks and the funded two-spare-barrel
  ledger (magazine or warehouse), consumes the
  first gun's initial embedded barrel only, moves the disposable visitor beyond direct-fire range
  and drafts it, then observes the real funded crew's native jobs. Resume after
  arming; require fresh `P4E_LOGISTICS_PROBE_COMPLETE` with `passed=True`. It
  automatically pauses on success/deadline. Do not leave an undrafted visitor
  running unattended: its death can unload the test map before inspection.
  Use `Audit P4E mortar logistics` and `Show P4E mortar position` while paused.
  Invocation success alone is not a loading pass. Save/reload and compare stack
  IDs/counts plus loaded shells, not just loose-stock counts.
  `P4E move funded spare barrels to warehouse` moves the same existing two-barrel
  reserve onto available regular storage shelves, adding no stock. Use it before
  the loading probe to verify native warehouse fetching. A drained embedded barrel
  plus one fewer spare is consumption, not a grant of replacement supplies.
  Other guns may fire before the last crew loads; the probe therefore bounds
  remaining HE rather than requiring twelve minus gun count exactly. Its
  `firedBeforeAllReady` diagnostic records that native consumption. The
  nine-/ten-resident budget actions select funded ordinary wealth once, not
  additional crew. `P4E ignite magazine hazard probe` starts a native shell wick
  and automatically pauses 120 ticks after the selected stack is destroyed;
  require `P4E_MAGAZINE_HAZARD_COMPLETE`, and preserve a pre-hazard save first.
  This deliberately destructive disposable test is not evidence of blast immunity.
- P4E autocannon probes are disposable-only and auto-pause. Preserve a pre-probe
  save. They explicitly consume existing artillery ammunition to isolate
  direct-fire behavior, never add stocks/crew, and move the existing visitor.
  Use firing, rearm, power-loss and close-support actions separately; require
  fresh P4E_AUTOCANNON_PROBE_COMPLETE with the expected phase and passed=True.
  Rearm deliberately drains the loaded magazine, then requires a funded worker
  and actual finite-steel consumption. Power loss removes owned conduits.
  Reload the pre-probe save afterwards. Native smoke effects are queued:
  P4E pop funded logistics smoke once consumes an existing charge; resume and
  require P4E_LOGISTICS_SMOKE_OBSERVED at the original pop cell after15ticks.
- Quest/native fallback tests have different terminal events; use the bounded
  contracts in `docs/p4d-quest-plan.md` and `docs/p4d-findings.md`, not the procedural
  completion pattern above.
  Fresh starts leave the guarded generator disabled by default. Before an
  adapter test, check the BOOT/DEBUG_TOGGLE evidence and use `Toggle guarded
  settlement generator` only if disabled; require `enableP0Generator=True`.
  A quest reporting `reason=disabled` is native-routing evidence, not an
  adapter pass. Ordinary debug generation enables it for that running process.

All test profiles, save copies and logs remain ignored under `.runtime/`.

For late rollback verification, capture `GET /api/v1/map/things?map_id=ID` before
and after the forced failure and compare physical thing IDs, definitions and
stack counts. Require `itemLedgerRestored=True` as well as terrain/plant recovery.
Floor undo must not refund deconstruction resources. Wall undo also queues native
roof collapses: the transaction restores the pre-existing queue, and the subsequent
retry must survive resumed ticks, not just its paused generation audit.

## P5 encounter probes

`Audit P5 finite encounter readiness` copies actual operating items, residents'
needs, installed guns, fuel multipliers, loads and charge. It excludes the native
sale holder and credits no new harvest/manufacture. Its three-day/six-hour
calculations are **not** elapsed-horizon acceptance. Use the explicit input/duty
and actual/rated outage fields; lower current draw is not the rated-load case.

`Start P5 three-day routine probe` saves a pre-probe point, parks the same
disposable visitor in the developer home map, and explicitly holds only this
running ordinary encounter against automatic map unloading. Native defeat is
unchanged. This test-only hold adds no NPC/stock/needs/output, and must never be
counted as native removal/revisit evidence. Resume actual game ticks and require
fresh `P5_ROUTINE_PROBE_COMPLETE` with `passed=True`, `elapsed>=180000`, all
original residents eating and sleeping in actual beds, real fuel increases and
zero sampled starvation/downing/loss. Paused wall time is not credited. Recheck
state during intermediate pauses; an explicit user pause ends test work.
The probe auto-pauses and restores the visitor if still alive on completion.
The parked test actor's survival is not this NPC operation gate; restore the
untouched baseline before independent probes. Reload during the
probe explicitly interrupts its incomplete measurement; repeat from the named
pre-probe save. Do not use a captive visitor to hold a multi-day routine test:
hostile Guest status is illegal, and a stationary captive can starve independently
of the funded residents. Test actions resolve/log one unique supported encounter
if reload selected the home view, and reject missing/ambiguous targets.

`P5 acquire current ordinary offer once` is an explicit mutable native-stock
boundary; `Audit P5 native stock ownership` is read-only and does not invoke its
lazy getter. At the initial spike checkpoint, the native holder remains sole
owner—no physical trade-stock materialization or full P5 completion is implied.

Normal funded generation now materializes supported sale goods. For current
ownership use `Audit P5 physical sale stock and reserves`: the base scalar ledger
excludes allocated sale goods deliberately; `P5_ALLOCATED_AUDIT` reports those
actual objects separately. `P5 test emergency transfer rollback` requires a real
exhausted category and checks exact sale/consumer restoration without adding stock.
`P5 unload current settlement only` permits off-map save/reload, and
`P5 reopen saved allocated-stock settlement` restores one unique retained-stock
site. Recheck the generator toggle after a cold start and require accepted spawn
plus `P5_ALLOCATED_RESTORE recreated=0`; invocation alone is not proof.

P5.4: unload archives the surviving residents (pinned world pawns) and asset
state; re-entry restores them (`P5_RESIDENT_RESTORE generated=0 replaced=0`,
`P5_ASSET_RESTORE granted=0`). For off-map save/load use `P5 unload current
settlement only`, `P5 save off-map archive checkpoint`, cold-load that save, then
`P5 reopen saved allocated-stock settlement` (it accepts archived sites).

Player-free settlements can unload on the first reload tick even while paused.
Use `P5 attach existing test visitor` for mapped active-reload validation; it
moves/drafts an existing disposable colonist, never creates a pawn. Preserve named
saves before the P5 original-barrel/food exhaustion, allocated-barrel consumption
and ingredient-damage actions: they deliberately remove/damage existing inputs.
The P4E loading probe additionally accepts an explicitly allocated three-barrel
reserve and requires actual native consumption to two. Its usual two-barrel
fixture and old-save default remain unchanged. Raw ingredients are retained
inventory, not ready nutrition or an elapsed cooking/feeding pass.
